# 日志库拆分（event_logs 独立库）

`event_logs` 是全站最热的表：每次请求都会写一条消费日志（`RecordConsumeLog` →
`CreateLogWithFinanceRecords` 的三写事务），同时监控大盘、账务/采购报表、日志列表
又对它做大范围聚合查询。默认 `database.log_sql_dsn` 留空时，`LOG_DB` 直接复用主库
`DB` 和同一个连接池——业务写路径与后台分析查询互相抢连接，是“各种大盘/列表把系统
拖卡”的主因之一。

把 `event_logs` 拆到独立 PostgreSQL 库/实例后，写路径与分析查询各用一套连接池，
互不阻塞。

## 何时需要拆

出现以下任一情况就建议拆：

- 打开监控大盘 / 账务报表 / 日志列表时，接口明显变慢甚至拖慢正常 API 调用。
- PostgreSQL 活跃连接经常顶到 `max_connections`，或大量连接卡在日志聚合查询上。
- 单库磁盘/IO 被 `event_logs` 的写入与全表扫描占满。

数据量不大、只有单实例、没有明显卡顿时，可以先不拆，仅靠已有的短 TTL 大盘缓存
和热点索引即可。

## 拆分步骤

### 1. 准备独立库

新建一个 PostgreSQL 库（可以是同实例的另一个 database，更彻底是另一台实例）。
只支持 PostgreSQL。首次启动时 Router 会在该库自动建 `event_logs` 及其索引
（走 `log` scope 的版本化迁移），无需手工建表。

### 2. 配置 log_sql_dsn

在 `config.yaml` 的 `database` 段填入独立库 DSN：

```yaml
database:
  sql_dsn: "postgres://user:pass@main-host:5432/router?sslmode=disable"
  # 独立日志库；留空则复用 sql_dsn
  log_sql_dsn: "postgres://user:pass@log-host:5432/router_logs?sslmode=disable"
  max_idle_conns: 25
  max_open_conns: 50
  max_lifetime_seconds: 300
```

对应环境变量为 `LOG_SQL_DSN`。留空（默认）即复用主库。

### 3. 连接池预算

连接池上限是“每实例 x 每库”生效的。启用独立日志库后，单个 Router 实例最多会开：

```
主库连接 + 日志库连接 = 2 x max_open_conns
```

多实例部署时再乘以实例数。务必保证

```
实例数 x 2 x max_open_conns  <=  PostgreSQL 的 max_connections（两个库分别核算）
```

默认 `max_open_conns: 50` 对单实例足够；横向扩容前先复核这条不等式。

### 4. 重启并验证

重启后日志里应出现：

```
using secondary database for table event_logs
secondary database migration started
secondary database migrated
```

随后确认：

- 独立库中已生成 `event_logs` 表及索引（`idx_event_logs_channel_created_at` 等）。
- 监控大盘、账务报表、日志列表能正常读取（读的是新库）。
- 主库的连接压力明显下降。

## 历史数据迁移（可选）

拆库后，新写入的日志进独立库，**旧日志仍在原主库**。是否搬迁历史数据看需求：

- **不搬**：报表/大盘只统计切换后的数据；旧日志保留在主库，需要时单独查。最简单。
- **搬迁**：停写或低峰期，用 `pg_dump -t event_logs` 从主库导出、导入独立库，
  再删除主库旧表数据。搬迁前务必备份，并核对 `event_logs` 表结构一致
  （两库由同一套 `log` scope 迁移生成，结构应当一致）。

## 回退

把 `log_sql_dsn` 改回空并重启即可复用主库。注意：回退后写入会回到主库，
独立库里的日志不会自动合并回来，报表会缺这段数据。回退前同样先评估历史数据处理。
