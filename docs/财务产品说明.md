# 财务产品说明

本文档定义 Router 管理端“财务”一级目录的产品定位、页面职责、数据口径、下钻关系和持续优化约束。

它是财务产品形态的当前基准。调整财务导航、页面布局、指标、筛选、下钻或治理动作前，应先对照本文档，避免重新把总览、分析和配置混入同一个页面。

## 1. 产品目标

Router 财务模块服务于模型路由业务的经营判断，不是通用会计系统，也不是充值流水或用户余额后台。

财务模块必须持续回答三个问题：

1. Router 当前整体财务是否健康？
2. 哪些模型、渠道或端点存在利润问题？
3. 采购成本依据是否完整，异常成本如何修复？

对应三个页面：

| 页面 | 路径 | 定位 | 核心动作 |
| --- | --- | --- | --- |
| 财务 / 总览 | `/admin/finance/overview` | 全局经营判断 | 发现异常并选择下钻方向 |
| 财务 / 利润 | `/admin/finance/profit` | 模型利润诊断 | 定位低毛利、亏损和数据不足 |
| 财务 / 采购 | `/admin/finance/procurement` | 成本事实治理 | 维护采购记录并处理成本归因 |

三个页面的关系是：

```text
总览用于判断
利润用于诊断
采购用于治理
```

## 2. 财务数据口径

Router 的核心财务关系：

```text
计费收入 - 采购成本 = 毛利
毛利 / 计费收入 = 毛利率
```

### 2.1 计费收入

计费收入是用户请求实际结算后形成的销售金额，不是充值金额，也不是用户账户余额变化。

用户充值只表示现金流入和用户资产增加。只有请求完成结算，才形成当前财务模块使用的计费收入。

### 2.2 采购成本

采购成本是 Router 使用上游渠道资源所承担的实际成本。其依据可以来自余额充值、周期额度、套餐包、模型专属包、端点专属包或明确的零成本配置。

采购成本必须能追溯到采购记录、采购批次和请求消费。缺失成本不能按零成本处理。

### 2.3 毛利与毛利率

毛利只基于已经获得可信成本的请求计算。成本未配置、待归因、归因失败或仅有估算成本时，不能把表面上的高毛利判定为正常盈利。

### 2.4 成本覆盖

成本覆盖表示当前请求中有多少已经获得可用于正式财务判断的采购成本：

```text
成本覆盖率 = 已配置成本请求数 / 总请求数
```

成本覆盖不足时，毛利结论不完整。总览和利润页面必须同时展示盈利结果与成本覆盖，不能只展示毛利数字。

### 2.5 YYC 与基础币种

- `YYC` 是用户侧统一结算资产。
- `CNY` 是当前财务报表统一比较收入、成本和毛利的基础币种。
- Router 消耗 YYC 表示用户权益结算结果，不等同于 CNY 收入。

## 3. 财务 / 总览

路径：

```text
/admin/finance/overview
```

### 3.1 页面定位

总览是财务驾驶舱，用于快速判断当前经营结果是否正常，不负责维护采购记录，也不负责展示请求级成本明细。

总览首先回答：

1. 最近计费收入、采购成本和毛利是多少？
2. 毛利率是否符合预期？
3. 成本覆盖是否足以支持当前结论？
4. 是否存在需要立即处理的异常？
5. 应该进入利润还是采购继续处理？

### 3.2 核心指标

总览应优先展示：

1. 计费收入。
2. 采购成本。
3. 毛利。
4. 毛利率。
5. 成本覆盖率。
6. 异常项数量。

默认时间范围可以使用最近 7 天，但必须明确时间口径，并允许按渠道和模型缩小范围。

### 3.3 异常识别

总览需要识别并排序以下问题：

1. 请求缺少采购成本。
2. 模型正式毛利为负。
3. 模型毛利率过低。
4. 售价触发成本底线。
5. 请求只能使用估算成本。
6. 成本仍待归因。
7. 成本归因失败，需要重试。
8. 采购批次或财务配置异常。

### 3.4 页面边界

总览应该保留：

- 少量关键指标。
- 高优先级异常。
- 渠道或模型的简要经营表现。
- 收入、成本和毛利趋势。
- 进入利润和采购的明确入口。

总览不应该放入：

- 采购记录编辑表单。
- 采购批次完整明细。
- 请求级成本流水。
- Billing 服务原始响应。
- 大量只用于技术排查的内部字段。
- 与经营判断无关的装饰性卡片。

## 4. 财务 / 利润

路径：

```text
/admin/finance/profit
```

### 4.1 页面定位

利润是模型维度的经营诊断页。总览发现整体异常后，利润页面负责定位具体是哪个模型、分组或价格关系出现问题。

利润页面回答：

1. 哪些模型正常盈利？
2. 哪些模型毛利过低？
3. 哪些模型售价已经低于采购成本？
4. 哪些模型因为成本覆盖不足而无法判断？
5. 问题更可能来自售价、倍率还是采购成本？

### 4.2 核心字段

模型列表至少需要展示：

1. 模型。
2. 利润状态。
3. 请求数。
4. 计费收入。
5. 采购成本。
6. 毛利。
7. 毛利率。
8. 成本覆盖。

### 4.3 利润状态

当前基础状态：

| 状态 | 含义 |
| --- | --- |
| 正常 | 成本已覆盖，毛利率达到健康标准 |
| 低毛利 | 售价覆盖成本，但毛利率低于目标 |
| 低于成本 | 采购成本超过计费收入 |
| 数据不足 | 成本缺失、待归因、归因失败或只有估算成本 |

“数据不足”必须优先于表面盈利判断。只要存在影响可信度的成本缺口，就不能把模型标记为正常。

### 4.4 页面边界

利润页面应该聚焦模型比较和异常定位，不直接承载复杂采购录入。

利润页面不应该：

- 复制总览的全部指标和趋势。
- 直接展示渠道采购表单。
- 把成本未知显示成零成本。
- 只按毛利金额排序而忽略成本覆盖。
- 自动修改售价或倍率。

后续增强应优先增加从异常模型下钻到关联渠道、采购成本来源和价格决策的路径。

## 5. 财务 / 采购

路径：

```text
/admin/finance/procurement
```

### 5.1 页面定位

采购是上游成本事实和成本归因治理页，是利润计算的数据基础。

采购页面回答：

1. Router 从哪个渠道采购了什么资源？
2. 采购金额、币种、有效期和可用容量是多少？
3. 请求为什么没有获得采购成本？
4. 哪些请求仍待归因或归因失败？
5. 应如何补齐采购记录或修复成本归因？

### 5.2 总览层

采购总览允许按渠道、模型或端点观察请求成本，并支持只查看未配置成本的请求。

总览层需要展示：

- 请求数。
- Router 消耗 YYC。
- 用户侧售价。
- 已归因采购成本。
- 毛利和毛利率。
- 已配置成本请求数。
- 未配置成本请求数。
- 待归因和归因失败数量。

总览层用于发现需要治理的渠道，不直接混合所有渠道的采购记录编辑器。

### 5.3 渠道下钻层

点击渠道后进入：

```text
财务 / 采购 / 渠道名称
```

渠道详情只维护当前渠道的采购记录。新增记录必须绑定当前下钻渠道，不应再次要求用户从“全部渠道”选择器中选择。

采购记录至少包含：

- 采购时间。
- 采购币种。
- 实际支付金额。
- 汇率和基础币种成本。
- 权益名称。
- 有效期。
- 额度、余额、Token、次数或套餐权益。

### 5.4 成本形成链路

```text
采购记录
  ↓
采购批次
  ↓
请求消费采购容量
  ↓
请求获得采购成本
  ↓
模型获得可信毛利
```

采购记录是事实入口，采购批次是成本分摊载体，请求消费是成本归因结果。三个层级必须可追溯，不能用最新余额覆盖历史采购事实。

### 5.5 异常治理

采购页面需要处理：

1. 没有可用采购批次。
2. 采购批次成本未配置。
3. 采购容量不足或过期。
4. 请求模型、端点与采购范围不匹配。
5. 成本归因失败。
6. 成本归因需要重试。
7. 只有估算成本，缺少正式成本。

### 5.6 页面边界

采购页面不应该：

- 用“全部渠道”表示一个实际不存在的采购记录集合。
- 在总览和渠道编辑器之间混用两个渠道状态。
- 把 Billing 服务账户余额直接当作采购成本。
- 把采购记录、采购批次和请求消费混成同一张表。
- 在没有明确渠道上下文时允许新增采购记录。

## 6. 三个页面的闭环

标准处理流程：

```text
1. 总览发现成本覆盖率下降或异常数量增加
2. 利润定位到低毛利、亏损或数据不足的模型
3. 采购按模型或渠道找到未配置成本请求
4. 下钻到渠道，新增或修正采购记录
5. 对失败记录执行成本归因重试
6. 返回利润确认成本覆盖和利润状态
7. 返回总览确认整体指标恢复正常
```

页面之间不是平级数据副本，而是逐层缩小问题范围：

```text
全局经营状态
  ↓
模型利润问题
  ↓
渠道采购事实
  ↓
成本归因修复
```

## 7. 持续优化原则

### 7.1 一个页面只承担一个主要任务

- 总览负责判断。
- 利润负责诊断。
- 采购负责治理。

新增功能前必须先判断它属于哪个任务。无法明确归属的功能，不应直接加入现有页面。

### 7.2 先下钻，再展开细节

全局页面不展示所有渠道记录，模型页面不展示所有采购字段。用户应通过明确的链接和面包屑逐层进入具体对象。

### 7.3 指标必须带可信度

毛利、毛利率和单位成本必须同时考虑成本覆盖和成本来源。估算值、待归因值和正式值必须能区分。

### 7.4 页面名称使用业务对象

一级页面名称使用“总览”“利润”“采购”，避免使用实现型名称或把报表类型写进导航。

API 可以继续使用 `procurement-report` 等技术名称，但页面路径和导航应表达用户任务。

### 7.5 操作必须有明确上下文

新增、编辑和删除采购记录时，渠道上下文必须唯一，并体现在 URL、面包屑和请求路径中。

### 7.6 避免卡片堆叠

财务后台是高频运营工具。优先使用紧凑指标带、表格、状态条和清晰分区，避免用大量装饰性卡片制造虚假层级。

### 7.7 不自动掩盖异常

- 缺失成本不能按零成本。
- 估算成本不能冒充正式成本。
- 保存成功后必须重新读取服务端数据。
- 归因失败必须可见、可重试、可审计。

## 8. 产品变更检查清单

调整财务产品前检查：

1. 该功能属于判断、诊断还是治理？
2. 是否放在了正确页面？
3. 是否需要通过下钻进入，而不是直接堆在总览？
4. 指标是否说明时间范围、币种和成本可信度？
5. 是否错误地把充值、余额、YYC 消耗和计费收入混为一谈？
6. 是否错误地把 Billing 服务余额当作采购成本？
7. 是否存在“全部渠道”但实际没有聚合数据的误导状态？
8. 保存后是否按实际对象重新加载？
9. URL、面包屑和操作对象是否一致？
10. 是否同步更新本文档、计费架构和必要的 OpenAPI？
